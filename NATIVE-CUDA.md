# Separate native CUDA execution profile

The additive `embedded-zimage-cuda-fp32` backend and `embedded-zimage-cuda` command expose a separately fingerprinted FP32/math CUDA response cohort. The existing CPU backend, graph source, source lock, initialization policy, row protocol and old packets retain their original bytes. No CPU packet or frozen-row file is relabeled for CUDA.

This profile prepares raw native latent velocity fields and the same actual HNDL adapter-only G/D game. It has no particle bank, native image renderer or pretrained quality qualification. The existing `zimage-fixture` shared-dispatch profile remains CPU-only. New CUDA hardware, full-model resources and learning rates require separate measured qualification; CPU software fixtures cannot establish those claims.

Before starting a CUDA process, set `CUDA_VISIBLE_DEVICES` to exactly one physical `GPU-…` UUID and `CUBLAS_WORKSPACE_CONFIG=:4096:8`. The caller owns resource admission, locks, memory limits and a free-memory guard. The CLI explicitly configures strict deterministic algorithms, TF32 off, cuDNN benchmark off/deterministic on, and math SDPA with flash, efficient and cuDNN SDPA disabled. API callers set these same flags themselves or call `execution.configure_execution_profile()` before CUDA initializes. Policy validation only reads settings; it neither initializes CUDA nor silently changes them.

Options must explicitly select `runtime_profile='native-cuda-fp32-math-v1'`, `device='cuda:0'`, and FP32. The identity binds the exact Torch/CUDA build, numerical flags, checkpoint mode, CUDA backend and execution source hashes, native Diffusers source, full pinned core/PG/HNDL closure, and the streamed local bundle config/weight digest. Physical UUID is checked for ownership and belongs in execution receipts, while portable weight identity uses logical device0. No unrelated CUDA generator is initialized, seeded or snapshotted. Initialization forks/seeds CPU and only visible CUDA device0, with distinct preparation/loader/adapter/critic streams.

Use `cuda_backend.bundle_identity(model_dir, options=options)` and write a fresh frozen rows file with `cuda_backend.PROTOCOL`, that model identity and actual preencoded native rows. Raw row tensors remain finite FP32 CPU storage with the existing native `[1,C,H,W]` shape; the controlled factory stages them onto the owned CUDA device and computes fresh native teachers there. A CPU rows file is rejected by the new protocol. The model bundle remains local unsharded FP32 safetensors/config, with native patch2/temporal1 geometry; no model download or dtype conversion is implicit.

The common `open_response(SessionConfig(...))` and native-only `open_inference(...)` APIs discover the new backend through separate entry points. The CUDA CLI accepts the same base/critic rate overrides as the CPU command. Raw export and no host EMA remain defaults; EMA requires an explicit decay experiment. `prior_lr_mult` is refused because no bank exists.

Optional `gradient_checkpointing=True` is a different identity. The native model must start uncheckpointed; the profile owns enablement and binds the public shared scale-aware checkpoint hook before backward. Closure restores the borrowed checkpoint callbacks, enablement flags, module modes, requires-grad state and owned adapter hooks. Repeated retained-gradient/backward scale checks are covered by CPU native-block software tests; real CUDA replay still needs a separately admitted proof. Runtime numerical and checkpoint flags are rechecked before each native forward.

CPU checks cover policy refusal before allocation, one-UUID admission, private initialization scopes, actual tiny native/HNDL updates and exact split resume through a clearly marked CPU placement fixture, raw inference after dataset deletion, execution-source mismatch refusal, CPU row-protocol rejection, signed scale/checkpoint VJPs, cleanup and raw/no-EMA CLI defaults. They preserve the existing58 CPU regression tests. They do not claim actual CUDA or pretrained qualification.
